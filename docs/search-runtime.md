# MS1-02 / SEA-40 — 2.4 - 2.5. Graceful degradation, обработка ошибок, отмена операций

## 1. Общие архитектурные допущения

1. Поиск обращается к трём независимым источникам: Catalog, Offers, Reviews.
2. Все три обращения запускаются параллельно.
3. Для каждого источника используется отдельный `CompletableFuture`.
4. CPU-обработка продуктов (фильтрация и ранжирование) выполняется в отдельном `cpuExecutor`.
5. Для MVP используем стандартный `CompletableFuture`, без собственной абстракции `Task<T>`.
6. Graceful degradation означает, что ошибка одного компонента не обязательно приводит к отказу всего поискового запроса.

## 2. Обработка ошибок внешних источников

7. Ошибка отдельного источника не должна автоматически завершать весь поисковый запрос исключением.
8. Каждый результат источника нормализуется в `SearchBox<T>`:
    - успешный результат содержит данные и `error == null`;
    - неуспешный результат содержит пустой список и `SourceError`.
9. Пустой список считается допустимым успешным результатом, а не ошибкой.
10. `null` вместо списка считается некорректным ответом источника.
11. Исключение при синхронном вызове клиента также преобразуется в `SourceError`.
12. Исключение при асинхронном выполнении источника преобразуется в `SourceError`.
13. Некорректный список, например содержащий `null`, также считается ошибкой ответа источника.
14. Ошибки источников сохраняются в итоговом `SearchResultBox.errors`.

## 3. Полный отказ источников

15. Если все три источника завершились ошибкой, весь поисковый запрос завершается с `AllSourcesUnavailableException`.
16. Если хотя бы один источник успешно вернул результат, поиск продолжается.
17. При частичном отказе источников данные успешно ответивших источников сохраняются.
18. Ошибки недоступных источников не теряются и возвращаются вместе с результатом.

## 4. Обработка ошибок CPU-этапов

19. Фильтрация и ранжирование — независимые стадии обработки продуктов, но выполняются последовательно.
20. Если Catalog завершился ошибкой, фильтрация и ранжирование не запускаются.
21. Если фильтрация завершилась ошибкой:
    - продукты заменяются на пустой список;
    - формируется `ProcessingError`;
    - ранжирование пропускается.
22. Если ранжирование завершилось ошибкой:
    - используется результат фильтрации;
    - формируется `ProcessingError`;
    - Offers и Reviews сохраняются.
23. Ошибка CPU-обработки не должна приводить к потере успешно полученных Offers и Reviews.
24. Ошибки CPU-этапов сохраняются отдельно в `SearchResultBox.processingErrors`.
25. `ProcessingBox<T>` хранит либо успешно обработанные данные, либо fallback вместе с ошибкой.
26. `null` в качестве результата CPU-обработки считается ошибкой обработки.
27. Некорректный результат CPU-обработки, который не удаётся скопировать через `List.copyOf()`, также считается ошибкой.

## 5. Итоговый результат

28. `SearchResultBox` содержит три составляющие:
    - `SearchResult` — доступные данные;
    - `List<SourceError>` — ошибки внешних источников;
    - `List<ProcessingError>` — ошибки обработки.
29. Все списки ошибок в `SearchResultBox` неизменяемы.
30. `isSuccessful()` возвращает `true`, только если отсутствуют и ошибки источников, и ошибки обработки.
31. Таким образом, частичный результат может быть возвращён, но при этом считаться неуспешным по `isSuccessful()`.

## 6. Таймауты

32. У каждого внешнего источника есть собственный timeout.
33. Источник, превысивший собственный timeout, считается неуспешным и формирует `SourceError` с кодом `TIMEOUT`.
34. Общий request deadline — жёсткий end-to-end лимит.
35. Он включает ожидание источников, фильтрацию, ранжирование и формирование итогового результата.
36. Если итоговый результат не готов к deadline, вызывающий код получает `TimeoutException`.
37. Общий timeout не превращается в частичный результат автоматически.
38. `orTimeout()` не гарантирует физическую отмену upstream futures или уже выполняющихся CPU-задач.
39. Общий deadline использует механизм `CancellationContext` для отмены зарегистрированных операций.
40. Локальный timeout внешнего источника приводит к отмене соответствующего физического транспорта.

## 7. Логика композиции CompletableFuture

41. `CompletableFuture.allOf()` используется для ожидания завершения всех трёх нормализованных futures источников.
42. После `allOf()` используем `join()`, поскольку futures уже завершены и не требуется блокирующее ожидание.
43. `thenCompose()` используется для перехода от завершения фильтрации к асинхронному запуску ранжирования.
44. `thenApply()` используется для преобразования результата ранжирования в `SearchResultBox`.
45. `handle()` используется для преобразования успешного или исключительного завершения в нормализованный `SearchBox` / `ProcessingBox`.
46. Для защиты future источника от изменения через `orTimeout()` создаётся отдельный future с помощью `thenApply(Function.identity())` (или `copy()`).
47. Синхронные исключения при запуске задач, в том числе `RejectedExecutionException` от `cpuExecutor`, обрабатываются отдельно.

## 8. Отмена операций — CancellationContext

48. На один поисковый запрос создаётся один `CancellationContext`.
49. Каждая отменяемая операция регистрируется в контексте отдельно.
50. Операцию можно снять с регистрации после её завершения.
51. Повторный вызов `cancel()` безопасен и не приводит к повторной отмене операций.
52. Регистрация новой операции после отмены контекста приводит к её немедленной отмене.
53. Вызовы cancellation actions выполняются вне `synchronized`-блока, чтобы не удерживать блокировку во время выполнения пользовательского кода.
54. Ошибка при отмене одной операции не мешает отмене остальных зарегистрированных операций.
55. `CancellationContext` координирует отмену операций, но не заменяет механизмы отмены конкретных типов задач.

## 9. Отмена CPU-обработки

56. Для запуска CPU-задач используется `FutureTask`, а не `CompletableFuture.runAsync()`.
57. `FutureTask.cancel(true)` позволяет прервать рабочий поток, выполняющий задачу, если код задачи реагирует на interruption.
58. Метод `FutureTask.done()` используется для передачи результата выполнения, исключения или отмены в отдельный `CompletableFuture`.
59. Отмена CPU-задачи не должна преобразовываться в `ProcessingError`.
60. После завершения CPU-обработки соответствующая операция снимается с регистрации в `CancellationContext`.
61. Использование отдельного `CompletableFuture` позволяет сохранить композицию асинхронных стадий, а `FutureTask` — получить механизм прерывания выполняющейся задачи.

## 10. Отмена внешних вызовов

62. `SourceCall` отделяет отмену логической операции от отмены физического транспорта.
63. Логическая отмена результата и физическая отмена HTTP/gRPC-вызова — разные действия.
64. `HttpSourceCall` использует `AtomicBoolean` для защиты от повторной отмены физического транспорта.
65. Локальный timeout источника приводит к отмене физического транспорта.
66. Глобальная отмена приводит к отмене физического транспорта и `result` соответствующего `SourceCall`.
67. Отмена внешнего вызова не должна приводить к повторной отмене транспорта.

## 11. Интеграция отмены в поисковый запрос

68. Отмена публичного `CompletableFuture`, возвращаемого поисковым запросом, приводит к отмене операций, зарегистрированных в `CancellationContext`.
69. Общий request deadline использует тот же механизм отмены, что и явный вызов `cancel()`.
70. Завершённые операции снимаются с регистрации, чтобы не хранить ненужные cancellation actions.
71. Завершённый поиск нельзя отменить задним числом: вызов `cancel()` после нормального завершения не должен приводить к отмене уже завершённых операций.
72. Отмена и исключительное завершение — разные состояния. Отмена должна сохранять семантику cancellation и не превращаться в обычную ошибку обработки.

## 12. Что пока не входит в реализацию

- Автоматические повторы запросов к источникам.
- Возврат частичного результата при срабатывании общего deadline.
- Повторная попытка фильтрации или ранжирования.
- Настройка отдельных timeout для фильтрации и ранжирования.
- Приоритизация источников и динамическое изменение их веса.
- Детальная классификация всех возможных ошибок внешних клиентов.
- Гарантированное прерывание CPU-задач, которые игнорируют interruption.
- Гарантированная физическая отмена внешнего транспорта, если конкретная реализация клиента не поддерживает отмену.

## Основной принцип

Максимально сохранить доступные данные при частичных отказах, явно зафиксировать причины деградации и завершать весь запрос ошибкой только при полном отказе источников либо нарушении общего request deadline.

Отмена является отдельным механизмом управления жизненным циклом поискового запроса: она должна распространяться на все зарегистрированные операции, включая CPU-задачи и внешние вызовы, не смешиваясь с обычной обработкой ошибок.
